# 视频下载软件第四版架构与实施计划

## 1. 基线结论

现有 v2.1 是 Windows/Tkinter 本地应用，已经具备 yt-dlp 页面解析、最高画质选择、FFmpeg 合并、进度、取消、Cookie、代理和本地历史。当前没有 FastAPI、云端任务系统、SwiftUI/Xcode 工程、GitHub Actions 或 Git 仓库。

## 2. 目标架构

```text
iPhone SwiftUI App
  -> HTTPS + Bearer API Key
FastAPI API
  -> SQLite（首个里程碑）
  -> 后台任务执行器（受控并发）
yt-dlp + FFmpeg
  -> 项目内/服务端受控存储
  -> 带时效的下载接口
```

首个可运行版本采用单机 FastAPI、SQLite 和进程内任务队列，避免一开始引入 Redis/Celery。部署扩容时再把队列替换为 Redis + 独立 Worker。

## 3. 代码边界

建议新增：

```text
server/
  app/
    api/
    core/
    models/
    services/
    workers/
  tests/
  requirements.txt
  Dockerfile
ios/
  VideoDownloader.xcodeproj
  VideoDownloader/
  VideoDownloaderTests/
.github/workflows/
  ios-build.yml
```

现有 `video_downloader/` 和 Windows 构建目录保持原样。服务端可迁移或包装以下逻辑：

- yt-dlp 格式选择和 FFmpeg 合并参数
- 媒体信息、格式与下载任务模型
- 结构化进度解析
- 文件名清理
- 错误翻译与日志脱敏

不得直接复用：

- 写死 `tools/windows-x64/*.exe` 的工具定位
- 使用 `taskkill.exe` 的进程终止逻辑
- Tkinter UI 线程和事件队列
- 本机浏览器 Cookie 读取方式

## 4. API 草案

所有 `/v1` 接口要求 `Authorization: Bearer <API_KEY>`。

| 方法 | 路径 | 用途 |
|---|---|---|
| `GET` | `/health` | 健康检查，不返回敏感信息 |
| `POST` | `/v1/media/analyze` | 解析 URL 和可用清晰度 |
| `POST` | `/v1/tasks` | 创建下载任务 |
| `GET` | `/v1/tasks/{id}` | 查询状态、进度和错误 |
| `POST` | `/v1/tasks/{id}/cancel` | 取消任务 |
| `POST` | `/v1/tasks/{id}/retry` | 失败任务重试 |
| `GET` | `/v1/tasks` | 下载历史 |
| `GET` | `/v1/tasks/{id}/file` | 下载完成文件 |
| `DELETE` | `/v1/tasks/{id}` | 删除任务和对应文件 |

任务状态统一为：`queued`、`analyzing`、`downloading`、`merging`、`completed`、`failed`、`cancelled`、`expired`。

首版使用轮询获取进度；稳定后再考虑 SSE，避免 WebSocket 增加首个 IPA 里程碑复杂度。

## 5. 服务端安全边界

- API Key 从环境变量读取，只存储摘要，不提交真实密钥。
- 对 URL 做协议、DNS 和重定向校验，阻止内网地址与本地文件，防止 SSRF。
- 限制任务并发数、单文件大小、最长时长、下载超时和每日请求量。
- 每个任务使用独立工作目录，输出路径必须经过服务端生成和校验。
- 下载完成文件设置过期时间并自动清理。
- 日志不得记录 Cookie、Authorization、API Key 或代理密码。
- 不提供 DRM、付费、会员或私密内容绕过。

## 6. SwiftUI 客户端

首个里程碑界面：

1. 首页 URL 输入框和解析按钮。
2. 视频信息、缩略图和清晰度选择。
3. 下载任务进度、取消与重试。
4. 历史任务列表。
5. 完成后使用系统文件导出；兼容视频使用 Photos 权限保存到相册。
6. 设置页保存服务器地址和 API Key；API Key 存入 Keychain。

最低功能应避免依赖付费账号受限的高级 capability。

## 7. IPA 构建路线

GitHub Actions 使用标准 macOS Runner：

1. 检出源码并选择固定 Xcode 版本。
2. 构建 iPhoneOS `Release` 产物，关闭云端代码签名。
3. 检查 `.app` 内主可执行文件、Info.plist 和嵌入框架。
4. 将 `.app` 放入 `Payload/` 并压缩为 IPA。
5. 上传 IPA、构建日志和校验值为 GitHub Actions Artifact。
6. Windows 下载 Artifact，解压得到 IPA，再交由 Sideloadly 使用用户自己的免费 Apple 账号重签。

此路径必须通过真实 GitHub 构建和真实 Sideloadly 安装验证；不能仅凭 ZIP 结构宣布成功。

## 8. 实施顺序

1. 初始化 Git 仓库并建立保护性基线提交。
2. 提取跨平台下载核心，保持 Windows 测试通过。
3. 实现 FastAPI 最小闭环和服务端测试。
4. 创建 SwiftUI 工程和 API 客户端。
5. 配置 GitHub Actions，生成未签名/待重签 IPA Artifact。
6. 在 Windows 使用 Sideloadly 实机安装。
7. 再补充云端部署、HTTPS、限流、清理和运维说明。

## 9. 阶段验收门

- Windows v2.1 功能和测试不得退化。
- 服务端下载与合并必须在 Linux 部署环境验证。
- SwiftUI 客户端不得内嵌下载站点网页。
- IPA 必须包含真机 arm64 应用，而不是模拟器构建。
- 最终里程碑以 Sideloadly 成功重签、安装并打开 App 为准。
